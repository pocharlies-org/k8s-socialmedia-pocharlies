# Optional Hindsight conversation memory

`SEMANTIC_PROVIDER=brain` preserves the upstream brain search and window jobs.
`SEMANTIC_PROVIDER=hindsight` routes semantic searches to the existing Hindsight
API and enables a separate resumable indexing worker in the rendered Compose.
No additional Hindsight server is installed.

Configure the private deployment `.env` using `deploy/.env.example`:

```dotenv
SEMANTIC_PROVIDER=hindsight
HINDSIGHT_URL=https://hindsight.staticduo.com
HINDSIGHT_BANK_ID=socialmedia-staticduo
HINDSIGHT_TIMEOUT_MS=10000
HINDSIGHT_RECALL_BUDGET=mid
HINDSIGHT_RECALL_MAX_TOKENS=4096
HINDSIGHT_SYNC_BATCH=100
HINDSIGHT_SYNC_INTERVAL_MS=30000
HINDSIGHT_SYNC_RETRY_MS=30000
HINDSIGHT_SYNC_SINCE=1970-01-01T00:00:00Z
HINDSIGHT_SYNC_CHAT_IDS=
HINDSIGHT_SYNC_EXCLUDED_PLATFORMS=
```

Set `HINDSIGHT_API_KEY` privately if the endpoint requires Bearer authentication.
The URL must be reachable from the MCP readers and worker. Credentials are never
sent to the browser, connectors or account registry.

Re-render and validate Compose using the commands in `deploy/README.md` before
recreating the affected services. The renderer adds `hindsight-sync` only when
the supplied environment selects Hindsight; it shares the API configuration with
`mcp-server` and `mcp-sse`, waits for migration success and joins the LLM network.
An ordinary `.env` change without re-rendering does not add/remove services.
The development root Compose uses the explicit `hindsight` profile; enable it
with `COMPOSE_PROFILES=hindsight` alongside `SEMANTIC_PROVIDER=hindsight`.
Apply migrations `033_hindsight_sync.sql` and `034_hindsight_conversations.sql`
before starting that worker. Published migration 033 remains unchanged.

## Storage and isolation

The default bank is exactly `socialmedia-staticduo`. Only dedicated names
`socialmedia`, `socialmedia-*` or `socialmedia_*` are accepted: `user-staticduo`
and other personal banks fail configuration validation. Initialization changes
only this bank's extraction mode to `chunks` and enables document text storage,
keeping literal conversations instead of generating LLM summaries. Hindsight
manages its native retrieval links; this integration does not replicate Brain's
Synapse/CO_OCCURS graph or request LLM entity extraction. There is one bank for
SocialMedia, with compound tags separating provider, namespace, provider account
and chat.

The worker indexes messages from enabled registry accounts, including WhatsApp,
Telegram and Instagram. Each conversation has one stable document ID derived
from provider, namespace, provider account, stored chat ID and Telegram topic.
Messages are ordered by timestamp and UUID, and added as JSONL turns under that
same document. The transcript includes the conversation title, real speaker
names, timestamps and PostgreSQL message UUIDs. Contact names come from the
account's stored address book and participants, with provider names as fallbacks;
an unavailable name is never invented. `HINDSIGHT_SYNC_SINCE`
and the optional comma-separated stored chat IDs bound the selected history.
Empty chat IDs mean every chat of enabled accounts.

Recall uses `all_strict` tags so untagged memories do not match. Returned document
IDs and tags are checked again against the confirmed local document-to-message
mapping, and PostgreSQL applies the authoritative account,
provider, conversation, sender, media, date and deletion filters. The application
returns exact database messages, never text generated by Hindsight. Semantic
outages or empty results fall back to text search with an explicit reason;
partial account failures keep successful results and report the unavailable scope.
The brain's `SEMANTIC_MIN_SCORE` is not applied to Hindsight scores.

## Resumable indexing

### Temporary platform pause

Apply migration `036_hindsight_platform_policy.sql`, then set
`HINDSIGHT_SYNC_EXCLUDED_PLATFORMS=telegram` in the deployment `.env` and recreate
only `hindsight-sync`. Empty/unset preserves indexing for all platforms. The
accepted names are `whatsapp`, `telegram`, `instagram`; invalid values fail
before changing the policy or making provider requests.

The worker mirrors this database-wide policy into `hindsight_sync_platform_policy`
under its destination lock. Run one consistent policy per source database.
Triggers skip excluded providers before scanning historical messages, and the
worker skips their queued documents and legacy pending operations. Provider
message/media synchronization keeps running. Existing Hindsight documents,
queue entries, revisions and pending operations are preserved; a pause does not
purge indexed history or cancel operations already accepted by Hindsight.

To resume, remove the platform from the exclusion list, recreate the worker and
reset its destination seed cursor (`seeded=false, seed_last_id=NULL` in
`hindsight_conversation_destinations`). This queues the history and changes made
during the pause in bounded batches while retaining document IDs and ledgers.
Already-indexed Telegram history remains searchable while new indexing is paused.

Migration 034 adds a conversation change queue and a ledger independent of the
legacy per-message ledger from migration 033. It does not rewrite history or
existing Brain cursors. Historical IDs are seeded in bounded batches only when
Hindsight is enabled. Edits, media enrichment, deletions and contact or title
changes queue new revisions; hard-deleted messages leave tombstones. Telegram
forum topics remain separate documents even when they share a group.

The first version stores a complete transcript with `replace`. When the confirmed
transcript is an exact prefix of the new version, only the added turns are sent
with `append`. An edit, deletion, earlier historical message or changed name
rebuilds the complete canonical transcript with `replace`, so the previous text
does not survive as an appended correction. An empty conversation removes its
document. Both modes preserve the document ID and use Hindsight delta retention.

Each submitted version has a persisted operation UUID. An acknowledgement means
accepted, and only the provider's completed operation marks it indexed. After a
restart or lost response the same operation is reconciled/reused. A pending old
version completes before an edit or deletion is submitted, preventing an old
asynchronous retain from recreating a deleted document. Failed operations remain
retryable; no failed message is skipped by advancing a shared scan cursor.

The ledger and confirmed message mapping are separate for each URL and bank, so switching providers or destinations
does not overwrite upstream ingestion progress. A destination advisory lock
prevents overlapping workers. `--once` runs one bounded pass; `--loop` or
`HINDSIGHT_SYNC_LOOP=true` runs continuously. Counts in worker logs distinguish
accepted, completed and failed operations; accepted is not a successful index.

Existing brain ingest/replay/window jobs skip or refuse writes when Hindsight is
selected. They resume their original behavior when `SEMANTIC_PROVIDER=brain`.
Switching back preserves the Hindsight bank and ledger for a later return.

The transition reconciles outstanding legacy operations before submitting
conversation documents. Existing per-message documents are preserved; retrieval
ignores their hits once a confirmed conversation document covers those messages.
Removing the old documents is a separate, explicit cleanup operation. No personal
bank is changed and no production bank is reset.

The installed append/delta and operation contracts were checked against Hindsight
0.10.1 and its official coding-session integration. The Brain provider retains
its existing window summaries and transport when selected.

## Optional integration tests

The ordinary server suite tests the HTTP contract and retry behavior without an
external Hindsight dependency. `hindsight-sync.integration.spec.ts` is opt-in:
`HINDSIGHT_TEST_DATABASE_URL` must target a disposable, fully migrated database
whose name starts with `hindsight_qa`. This enables real trigger/SQL validation
with a simulated provider, including a lost acknowledgement and hard deletion.
Adding `HINDSIGHT_TEST_URL` and, if required, `HINDSIGHT_TEST_API_KEY` also enables
the real retain/recall/edit/delete test in a unique `socialmedia-qa-*` bank.
These variables must never point at the production SocialMedia database.
